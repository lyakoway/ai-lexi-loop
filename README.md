# ai-lexi-loop

Персональный AI-тренажёр английского языка с доставкой уроков через Telegram.
Цель продукта — помочь пользователю быстрее начать понимать и самостоятельно
использовать английский: слова и выражения, перевод, IPA-транскрипция,
приблизительное произношение русскими буквами, примеры и аудио, позже —
упражнения и интервальные повторения.

Этот репозиторий — **этапы 1–5: фундамент, профиль, уроки, интервальные
повторения и SaaS-фундамент** (единая идентичность, публичный HTTP API,
продуктовая аналитика, статистика, наблюдаемость). Генерация выражений
через LLM, TTS и автоматическая отправка по расписанию здесь намеренно
отсутствуют; архитектура рассчитана на их добавление.

## Что уже есть

- FastAPI с health-эндпоинтами: `GET /health` (liveness) и `GET /ready`
  (readiness: проверка БД и статуса Telegram-polling).
- Telegram-бот на aiogram 3: `/start`, `/help`, `/lesson`, `/review`,
  `/stats`, `/token`, `/profile`, `/settings`, `/cancel` и пошаговый onboarding профиля на
  FSM + inline-кнопках.
- PostgreSQL через SQLAlchemy 2 (async): таблицы `users`, `profiles`,
  `expressions` и `expression_progress` (миграции Alembic с сидом словаря,
  CHECK-ограничения на уровне БД).
- Слоистая архитектура: handlers → services → repositories → db,
  Pydantic-схемы профиля, доменный слой со словарём продукта.
- pytest (unit + integration на реальном PostgreSQL), Ruff, Black, mypy
  (strict), pre-commit, GitHub Actions CI, Docker Compose.

## LLM-интеграция (этап 6.1 — фундамент)

Основа для AI-тьютора без пользовательских сценариев: протокол
`LlmClient` (Pydantic-контракт запроса/ответа) и три композиционных слоя
— OpenAI-совместимый провайдер на httpx (retry для 429/5xx/сетевых
сбоев, Retry-After, общий бюджет времени; 4xx без повторов),
наблюдающий слой (метрики `llm_calls_total`/`llm_errors_total`,
гистограмма `llm_latency_ms`, счётчики токенов, best-effort запись
`llm_calls` — только метрики, без промптов и ответов) и слой
структурированных ответов (Pydantic-валидация JSON + ровно одна
repair-попытка). Ошибки разделены по уровням: транспорт / провайдер /
формат вывода / конфигурация.

Включается явно (`LLM_ENABLED=true` + валидные `LLM_BASE_URL`,
`LLM_MODEL`, `LLM_API_KEY` — при ошибке конфигурации старт честно
падает); выключен по умолчанию — все функции продукта работают без
него. Бизнес-код зависит только от протокола в `app/integrations/llm`.

## SaaS-фундамент (этап 5)

### Идентичность пользователя

Внутренний аккаунт (`users.id`) отделён от способов входа: Telegram ID —
одна из записей в `user_identities` (`provider` + `provider_user_id`,
уникальная пара). Один аккаунт может иметь несколько идентичностей
(будущие email/OAuth добавятся записью с другим `provider`); один
Telegram ID не может принадлежать двум аккаунтам. Профиль, прогресс и
события связаны только с внутренним `user_id`, поэтому данные общие для
всех каналов.

### HTTP API v1 (для будущего Web Dashboard)

Аутентификация — персональный Bearer-токен: получить его можно командой
`/token` в Telegram (показывается один раз; в БД хранится только
SHA-256-хэш). Telegram ID из HTTP-запроса удостоверением личности не
является и не используется.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/profile` | текущий профиль (404, если не настроен) |
| PATCH | `/api/v1/profile` | изменение отдельных настроек (та же схема, что в боте) |
| POST | `/api/v1/lessons` | собрать урок (карточки или `unavailable_reason`) |
| GET | `/api/v1/reviews/due` | карточки к повторению |
| POST | `/api/v1/reviews/{expression_id}/answer` | ответ «Помню»/«Забыл» |
| GET | `/api/v1/stats/overview` | сводная статистика |
| GET | `/api/v1/stats/progress` | активность по дням (30 дней) |

Коды: 401 без/с неверным токеном, 404 для чужих или несуществующих
ресурсов, 422 для неверных значений, 503 при недоступной БД. Документация
— OpenAPI (`/docs`). Все endpoints изолируют данные по пользователю из
токена; бизнес-логика — те же сервисы, что и в Telegram.

### Продуктовая аналитика

События пишутся сервисами в общей транзакции с бизнес-изменением
(откат операции откатывает и событие) в `analytics_events`
(`source`: telegram/web, `properties` JSONB — только скалярные значения,
без текстов и секретов): `user_registered`, `profile_completed`,
`profile_updated`, `lesson_started`, `lesson_completed`,
`expression_shown`, `expression_completed`, `review_started`,
`review_answered` (с интервалами до/после), `review_completed`.
Повторные и устаревшие callback отклоняются до сервиса, поэтому не
дублируют события.

### Команды бота

`/stats` — изучено выражений, завершено уроков (с момента запуска
учёта), повторений, доля «Помню», ждут повторения, серия дней (по
timezone профиля); `/token` — выпуск персонального токена Web API.

### Наблюдаемость

Каждый HTTP-запрос получает `X-Request-ID` (или принимает входящий),
логируется с методом, путём, статусом и длительностью; в production логи
однострочные JSON. Счётчики `http_requests_total`/`http_errors_total`
отдаются в Prometheus-формате на `GET /metrics` (без пользовательских
данных). Ошибки Telegram-обработчиков логируются с трассировкой, ответы
пользователю не раскрывают внутренности.

## AI-тьютор: объяснение выражений (этап 6.2)

Первая AI-функция на фундаменте 6.1. Кнопка «🧠 Объяснить» на карточках
урока и повторения вызывает `TutorService.explain_expression`: карточка
+ родной язык + CEFR уходят в LLM (prompt `explain_v1`, текст выражения
передаётся как недоверенные данные в отдельном блоке), ответ
валидируется схемой `ExplanationOut` (значение, употребление,
особенности, частые ошибки, примеры, мини-диалог) и показывается в том
же сообщении с пометкой «сгенерировано AI» и кнопкой «⬅️ К карточке».
FSM урока/повторения не затрагивается — навигация и ответы продолжают
работать; объяснение ничего не пишет в SRS/прогресс. При выключенной
LLM или её ошибке пользователь получает честное сообщение и может
продолжить обучение; попытка фиксируется событием `tutor_explained`
(успех/причина, без контента). В API — `POST
/api/v1/expressions/{id}/explain` (Bearer; 404 для чужих/невыданных
выражений — без раскрытия существования; 503 при недоступной AI).
Права: объяснить можно только выражение, уже выданное пользователю.
Идемпотентный seed образцов для будущего evaluation —
`tests/data/tutor_explain_samples.json`.

## Интервальные повторения (этап 4)

Расписание повторений — упрощённый SM-2 с бинарными ответами
(`app/domain/srs.py`, чистые функции с передаваемым временем). Стартовое
состояние карточки: `ease=2.5`, интервал 1 день, 0 успешных повторений.
«Помню» → лестница интервалов 1 → 6 → `round(interval × ease)` дней;
«Забыл» → сброс счётчика, интервал 1 день, `ease × 0.8` (минимум 1.3).
Константы — прагматичные значения для MVP, а не научный оптимум.

Первое повторение карточки планируется в момент её выдачи в уроке
(`next_review_at = выдача + 1 день`), поэтому даже карточка из брошенного
урока возвращается через `/review`. `completed_at` сохраняет смысл
«урок доведён до конца» и на расписание не влияет.

`/review` показывает карточки, срок которых наступил (старейшие первыми,
до 20 за сессию): та же карточка, что и в уроке, и кнопки «Помню» /
«Забыл». Прогресс SRS хранится только в PostgreSQL (`expression_progress`:
`review_count`, `ease_factor`, `interval_days`, `next_review_at`,
`last_reviewed_at` — миграция 0004 с обратным заполнением существующего
прогресса); в FSM — только навигация сессии. Двойные нажатия и кнопки
старых сессий отклоняются сверкой токена и индекса; ошибка БД при ответе
показывает ошибку и оставляет карточку на месте — без ложного «успеха».

## Уроки (этап 3)

Домен выражений живёт в таблице `expressions`: выражение, перевод,
IPA-транскрипция, фонетическая подсказка русскими буквами (ударение —
заглавной гласной), пример с переводом, уровень CEFR, тема, флаг
активности. Уникальность `(language, text)` делает seed идемпотентным
(`ON CONFLICT DO NOTHING`): 16 стартовых выражений на четырёх уровнях и
пяти темах приезжают миграцией 0003.

Факт выдачи выражения пользователю хранится в `expression_progress`
(уникальная пара `user_id + expression_id`, `shown_at`, `completed_at`).
Выданное выражение никогда не показывается как новое снова — даже если
урок брошен на середине; `completed_at` отмечает пройденные карточки и
станет основой интервальных повторений этапа 4 (таблица будет расширяться,
а не заменяться).

### Как работает /lesson

1. Без профиля — приглашение пройти onboarding.
2. С профилем сервис подбирает новые выражения: тот же уровень CEFR
   (при `unknown` — явно A2 с пометкой в уроке), только выбранные темы
   (без выбранных — все), язык профиля, до `new_items_per_day`, исключая
   уже выданные. Порядок детерминированный (по id), подмена тем/уровня
   без ведома пользователя не делается — при нехватке приходит честное
   сообщение с причиной и подсказкой (`/settings`).
3. Карточки показываются по одной: выражение, IPA, русская подсказка,
   перевод, пример и его перевод + дисклеймер о приблизительности
   подсказки. Кнопки «Следующее» и «Завершить урок»; на последней
   карточке — только завершение.
4. Прогресс создаётся при сборке урока (атомарно с выборкой), завершение
   отмечает просмотренные карточки. Повторные и устаревшие нажатия
   отклоняются: каждый callback несёт токен урока и индекс карточки,
   которые сверяются с текущим состоянием FSM.

## Профиль обучения (этап 2)

Профиль хранится в таблице `profiles` (1:1 с `users`) и содержит: родной и
изучаемый язык, уровень CEFR (или `unknown`), цель, темы интересов, акцент,
минуты в день, количество новых выражений в день, время урока и повторения,
часовой пояс (IANA, не смещение UTC).

Выбор хранения тем — `ARRAY(String)` в PostgreSQL: это плоский список тегов
без собственных атрибутов, отдельная таблица была бы избыточной, а массив
позволяет будущему выбору уроков делать запросы вхождения (`topics @> ...`).

### Сценарий onboarding

11 шагов inline-кнопками: родной язык → изучаемый язык → уровень → цель →
темы (мультивыбор) → акцент → минуты в день → выражений в день → время
урока → время повторения → часовой пояс → экран подтверждения.

На каждом шаге доступны «Назад» (кроме первого), «Отмена», а для тем и
акцента — «Пропустить» (значения по умолчанию: нет тем, `us`). Часовой пояс
можно ввести текстом (город на русском/латиницей или имя зоны — например
«москва», «екб», `Europe/Riga`).

Повторный запуск (`/settings` → «Пройти настройку заново») начинает с
заполненными текущими значениями. Подтверждение полностью заменяет профиль,
сохраняя ту же строку (id и created_at).

### Команды бота

| Команда    | Действие                                            |
| ---------- | --------------------------------------------------- |
| `/start`   | новый пользователь → onboarding, Existing → меню    |
| `/profile` | показать сохранённый профиль                        |
| `/settings`| меню изменения отдельных настроек без полного опроса|
| `/cancel`  | отменить текущую настройку (данные не меняются)     |
| `/help`    | справка                                             |

### Поведение FSM при перезапуске

Черновик настройки и навигация текущего урока живут в памяти процесса
(MemoryStorage aiogram). При перезапуске приложения незавершённая
настройка и незавершённый урок теряются — пользователь начнёт заново.
Всё подтверждённое и весь прогресс уроков хранятся в PostgreSQL и
переживают рестарты: выданные выражения не покажутся как новые. Кнопки
старых сообщений после рестарта вежливо отклоняются: каждый callback
несёт шаг или токен урока и сверяется с текущим состоянием.

## Архитектура

Модульный монолит с явными границами слоёв:

```
app/
├── api/            FastAPI: фабрика приложения, роуты, обработка ошибок
├── bot/            Telegram: handlers, keyboards, middlewares, polling-раннер
├── core/           Конфигурация (pydantic-settings) и логирование
├── db/             Engine/сессии SQLAlchemy, ORM-модели
├── domain/         Словарь продукта: уровни, цели, темы, часовые пояса
├── repositories/   Доступ к данным (SQL), перевод ошибок БД в StorageError
├── schemas/        Pydantic-схемы профиля (валидация значений)
├── services/       Бизнес-логика (пользователи, профили)
└── main.py         Точка входа: python -m app.main
```

Ключевые решения:

- **Один процесс — два компонента.** FastAPI и Telegram polling запускаются
  вместе (`app/api/app.py` lifespan). Polling работает в отдельной
  наблюдаемой задаче (`app/bot/runner.py`): если он падает, `/ready`
  начинает отвечать 503, процесс не «притворяется» здоровым.
- **Handlers без бизнес-логики.** Обработчики бота только переводят
  обновления Telegram в вызовы сервисов. Сессия БД и сервисы попадают в
  обработчики через DI-middleware (`app/bot/middlewares/di.py`).
- **Никаких глобальных сессий.** Engine создаётся в lifespan приложения и
  передаётся явно; тесты полностью управляют зависимостями.
- **Миграции отдельно от приложения.** Приложение никогда не вызывает
  `create_all()`; схема создаётся командой `alembic upgrade head`
  (в Docker Compose — отдельный one-shot сервис `migrate`, поэтому
  несколько реплик приложения не применяют миграции одновременно).

Каталог `integrations/` (LLM, TTS, словари) из целевой структуры пока не
создан: реальных модулей для него на этом этапе нет. Появится вместе с
первой интеграцией.

## Быстрый старт (локально, без Docker)

Требуются: Python 3.12+, [uv](https://docs.astral.sh/uv/), PostgreSQL.

```bash
cp .env.example .env          # заполните DATABASE_URL и (опционально) токен бота
uv sync                       # создать .venv и установить зависимости из uv.lock
uv run alembic upgrade head   # применить миграции
uv run python -m app.main     # поднять API + бота
```

Проверка: `curl http://localhost:8000/health` и `curl http://localhost:8000/ready`.

Без `TELEGRAM_BOT_TOKEN` бот не запускается (`/ready` вернёт `"bot":
"disabled"`) — удобно для локальной разработки. В `ENVIRONMENT=production`
отсутствующий токен — ошибка старта.

## Быстрый старт (Docker Compose)

```bash
cp .env.example .env
docker compose up --build
```

Поднимаются PostgreSQL (с healthcheck и persistent volume), one-shot
сервис `migrate` (применяет миграции до старта приложения) и `app`.

## Переменные окружения

| Переменная           | Обязательна        | Описание                                     |
| -------------------- | ------------------ | -------------------------------------------- |
| `DATABASE_URL`       | да                 | строка подключения PostgreSQL                |
| `TELEGRAM_BOT_TOKEN` | в production       | токен из @BotFather                           |
| `ENVIRONMENT`        | нет (`dev`)        | `dev` / `staging` / `production`             |
| `HOST`, `PORT`       | нет (`0.0.0.0:8000`) | параметры HTTP-сервера                     |
| `LOG_LEVEL`          | нет (`INFO`)       | уровень логирования                          |
| `TESTING`            | нет (`false`)      | тестовый режим: отключает Telegram-polling   |

Секреты хранятся только в `.env` (в Git не попадает) или переменных
окружения; в настройках токен — `SecretStr`, в логи не пишется.

### Тесты

- `tests/unit/` — без сети и БД: настройки, фабрика приложения, `/health`,
  `/ready` (недоступная БД), обработчики `/start` и `/help`, lifecycle
  сессий, раннер polling, обработка ошибок.
- `tests/integration/` — реальный PostgreSQL: применение Alembic-миграций,
  уникальность `telegram_user_id`, репозиторий, `/ready` с живой БД.
  Запускаются только при установленной переменной `TEST_DATABASE_URL`,
  иначе пропускаются с явной причиной.

Пример запуска интеграционных тестов:

```bash
TEST_DATABASE_URL=postgresql://postgres:postgres@localhost:5432/ai_lexi_loop_test \
  uv run pytest
```

В CI (`.github/workflows/ci.yml`) PostgreSQL поднимается как service
container, поэтому интеграционные тесты выполняются всегда.

## Как добавить язык (language profile, этап 6.4.7)

Язык — это конфиг, а не код. Весь язык описывается одной записью
`LanguageProfile` в `app/domain/languages.py`:

```python
FRENCH = LanguageProfile(
    code="fr",
    name="French",
    label="🇫🇷 Français",            # подпись в кнопках и профиле
    explanation_language="ru",        # язык объяснений тьютора
    tts_voices={"us": "alloy", "uk": "onyx"},  # голос TTS по акценту
    show_ipa=True,                    # показывать IPA на карточках
    show_phonetic_hint=True,          # показывать русскую подсказку
    grammar_notes="...",              # брифинг грамматики для промптов
    diagnostic_question_count=6,      # длина диагностики уровня
    supported_accents=("us", "uk"),
)

LANGUAGE_PROFILES = {
    ENGLISH.code: ENGLISH,
    SPANISH.code: SPANISH,
    FRENCH.code: FRENCH,   # ← добавили
}
```

После этого автоматически: язык появляется в онбординге и в `/settings`
(метка из `label`), диагностика уровня генерирует вопросы нужной длины с
грамматическим брифингом, TTS берёт голос из `tts_voices`, карточки
следуют правилам транскрипции, промпты генерации получают имя языка.
Код менять не нужно.

**Честный scope:** из коробки полноценный — английский (акценты US/UK).
Испанский подключён как рабочий пример второй культуры: архитектура его
принимает, но каталог-словарь и качество контента — английские первыми;
карточки ES появляются через `/generate` (AI) и их качество не
гарантируется. Никакой другой язык не обещается пользователям, пока под
него не заведена запись профиля с реальным контентом.

Диагностика уровня («Не знаю — определить тестом» в онбординге)
генерирует 5–7 вопросов с LLM (`placement_v1`), оценка — детерминированное
правило в `app/domain/placement.py` (подъём по уровням CEFR при ≥50%
верных в группе), пользователь подтверждает результат. При выключенной
LLM диагностика недоступна — остаётся ручной выбор уровня. Прогресс при
смене языка/уровня/тем в `/settings` не сбрасывается: правится только
`profiles`, история повторений остаётся в плане.
